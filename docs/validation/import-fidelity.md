# Import fidelity: paste, xlsx and file encodings

2026-11-23. What reaches a table when data comes in by paste, by .xlsx or
by a text file, and what each check compares against. No engine numbers
change; `results-engine.md` (generated by the corpus runner) is untouched.

## Full-precision paste (P-05)

- Reference: `web/e2e-fixtures/clipboard/make_fixtures.py` writes
  `workbook.xlsx` with openpyxl 3.1.5 and `expected.json` from openpyxl's
  reading of it (stored value, number format, shown text).
- Clipboards: Excel (Windows with the CF_HTML header and 17-digit `x:num`;
  Mac with shortest `x:num`), Google Sheets (`data-sheets-value`) and
  LibreOffice Calc (`sdval`/`sdnum`). **Constructed from documentation, not
  captured**: sources are listed in the script's docstring. A real capture
  can replace any file; the checks read whatever the files hold.
- `e2e-check.mjs` pastes each clipboard into a column table. Acceptance
  column 0.123456, 0.234567, 0.345678 shown as 0.12, 0.23, 0.35: the cells
  hold the six-decimal values and the report reads "3 cells were shown
  rounded in Excel; the full values were used". Mixed block, cell by cell:
  numbers equal openpyxl's float exactly (1/3 as 0.3333333333333333,
  -0.000123456 shown as -1.23E-04, 12.4 shown as 12), percent (12.34%),
  date (2024-01-05) and text keep their shown text; 4 cells reported
  rounded for every app.
- Text-only paste: unchanged (0.12, 0.23, 0.35, no rounding sentence). HTML
  that does not line up with the text: the text, and the report says so.
- Not covered: thousands separators and currency formats keep their text
  (today's path). Paste-anywhere on the first-run screen read text only
  until 2026-11-24 (see "Wave 1 import gaps closed" below).

## xlsx import report (P-06)

- Reference: `web/e2e-fixtures/xlsx/make_fixtures.py` (openpyxl) writes
  workbook A (`=A2*2` to `=A6*2` with no cached values) and workbook B (an
  AutoFilter on A1:B10 with rows 4 to 6 hidden; a second sheet with row 3
  hidden by hand). `expected.json` holds openpyxl's normal-mode formulas,
  its data_only=True values (None for the five formulas) and its
  row_dimensions hidden flags.
- `lib/__tests__/xlsxFlags.test.ts` asserts the XML scan against
  expected.json: blank formulas B2, B3, B4, B5, B6; filter-hidden rows 4, 5,
  6; hand-hidden row 3. `e2e-check.mjs` drives the Import dialog: the
  report names the five cells; "3 rows are hidden by a filter in the
  workbook" ("in Excel" until 2026-11-24);
  the preview holds the six visible rows (doses 0.1, 0.3, 30, 100, 300,
  1000) until Keep the filtered rows makes it nine.
- Outside reference for B: Excel's copy behaviour, which cannot be run here.
  Microsoft's "Copy visible cells only" page says a filtered table copies
  only its visible cells and that a plain range copies hidden cells by
  default; the default here (filtered rows out, rows hidden by hand in)
  follows that split.

## File encodings (P-07)

- Reference: `web/e2e-fixtures/encodings/make_fixtures.py` writes one
  ImageJ results file ("Area (µm²)", "37 °C") as UTF-8, UTF-8 with BOM,
  UTF-16LE, UTF-16BE and Windows-1252, and a StepOne export headed "Cт"
  (Cyrillic te) as UTF-8, UTF-8 with BOM, UTF-16LE and UTF-16BE. No cp1252

## Pairing by subject ID (P-38), 2026-11-23

- Input: `web/e2e-fixtures/import/paired_long.csv`, mice M1 to M6 measured
  before and after, twelve records in a shuffled order (written by hand).
  Reference: the same values aligned by hand, one row per mouse
  (`engine/tests/reference/paired_by_id.py`, which checks that the file
  holds exactly those twelve values).
- Identity: `share/__tests__/pairing.test.ts` asserts that "From long
  table…" (paired) and the import recipes' column output both make the
  hand-aligned table, cell for cell, and that each row holds that mouse's
  own before and after values; reversing the records changes nothing.
- Paired t test of after - before on the aligned columns, scipy 1.18
  `ttest_rel` (R is not installed): t = 3.3128, df = 5, P = 0.021175, mean
  difference 1.70. Paired by the order of the records instead (the wrong
  pairing) it would be t = 2.5305, P = 0.0525. `e2e-import.mjs` fills a
  paired t test from the long table and reads t=3.313, df=5 and P value
  0.02117 in its results.
- Rules (unit and e2e tested): a subject with two records for one
  condition stops the import with a message naming the ID and its rows
  ("Subject “M3” has 2 records for “before” (rows 5 and 14)"); a subject
  missing a condition keeps its row with a blank and is listed as
  unmatched (the paired t test leaves incomplete pairs out and says so);
  records without an ID or a condition are left out and listed by row;
  values that are not numbers are kept as typed and counted. The recipes
  pair only when a subject ID appears in two or more groups: a design with
  different animals per group stacks the values as before.

Independent check of P-38 (2026-11-23, by the lead): pairing
`web/e2e-fixtures/import/paired_long.csv` by the mouse ID in own code
(M7 has no "after" and drops out) and running scipy.stats.ttest_rel on
after vs before gives t = 3.312806 on 5 df, P = 0.021175, the values the
app shows; pairing by record order would give t = 2.5305, P = 0.0525.

## Import provenance and replayed imports (P-76), 2026-11-24

- Each table made or refilled by the Import dialog, a recipe or Apply to
  new data records the file's name, size and SHA-256 (Web Crypto), the
  settings (the recipe with its plate map, or the delimiter, lines
  skipped, filters and column roles) and the values as imported (up to
  50,000 cells; above that a fingerprint only). The record is checked at
  import time: re-running the settings on the same file must give the
  table back exactly, or the record says why Apply to new data will put
  the next file into the table's layout instead (rows appended to a
  table, a text encoding chosen by hand, several files at once).
- Unit (`project/__tests__/importRecord.test.ts`): Web Crypto's SHA-256
  of `e2e-fixtures/plate-reader.csv` equals node's; the plate-reader
  recipe re-run on its own file gives the table byte for byte; one hand
  edit is counted; next week's file is read through the same recipe.
- e2e-share: plate-reader.csv through the recipe, one cell edited;
  History shows the file, its SHA-256 (equal to node's), the recipe and
  "1 cell edited by hand since the import" (3, row 3: 1.488 → 1.5);
  Apply to new data with plate-week2.csv re-runs the recipe and the
  table holds its readings (C1, C3 = 1.702, 1.527).
